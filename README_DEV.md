# PatternMaster Pro 开发与维护指南 🛠️

> **[IMPORTANT]** 
> 本文档记录了开发过程中最核心的数据库连接与驱动冲突解决方案。这是通过多次调试换来的宝贵经验，请在遇到“数据显示为空”或“打包失败”时优先参考。

---

## 🚀 核心方案：数据显示为空/后端崩溃 (ABI 冲突)

### ❓ 现象描述
运行 `npm run dev:all` 后，看板数据显示为空，或者终端显示 `正在关闭服务...`。这通常是因为 `better-sqlite3` 驱动版本与当前的 Node.js 环境不匹配。

### ✅ 终极三步修复法
如果数据不显示，**请务必按顺序执行以下命令**：

1. **彻底清理残留进程**（防止文件占用）：
   ```powershell
   taskkill /F /IM node.exe /T
   ```

2. **强制重新编译驱动**（适配当前 Node 环境）：
   ```powershell
   npm rebuild better-sqlite3
   ```

3. **重启项目**：
   ```powershell
   npm run dev:all
   ```

## 📦 打包与路径隔离方案 (V5.1 补丁)

### 1. 物理隔离：双端口机制
为了彻底防止开发环境（Vite）与生产环境（安装包）互相干扰，我们引入了**端口隔离**：
*   **开发环境后端**：运行在 `3001` 端口。
*   **生产环境后端**：运行在 `3005` 端口。
*   **前端适配**：`App.jsx` 中的 `API` 路径已改为动态自适应模式，它会自动根据访问来源找寻正确的后端接口。

### 2. 数据库路径锁定
生产环境数据库始终保持在：
`%APPDATA%\PatternMaster Pro\database.sqlite`

### 3. 经验总结：影子锁定 (Shadow Locking)
如果发现“先开开发环境正常，先开生产环境全挂”，说明生产环境应用在后台“暗中”尝试访问开发目录下的数据库文件并加了锁。
*   **解决方法**：已通过 `main.js` 强制指定生产环境的物理隔离路径。

## 🛠️ 打包冲突解决 (EPERM)
如果在打包（`npm run build:exe`）时遇到 `EPERM`，说明驱动被占用。
*   **解决方法**：先关闭所有终端窗口，再执行脚本。打包脚本已串联 `electron-rebuild`，会自动处理驱动适配。

## ⚠️ 已知架构缺陷：字段直接存储 vs ID引用

### 现象
当前 `tasks` 和 `styles` 表中的 `category`、`brand`、`designer` 等字段**直接存储字符串值**（如 `"ROM"`、`"连衣裙"`），而非关联到对应的 lookup 表（如 `brands.id`）。

### 风险
如果在"系统预设管理"中将品牌名 `"ROM"` 改为 `"ROM International"`，**已有单据中存储的仍是旧值 `"ROM"`**，导致数据孤岛。分类、设计师等字段同理。

### 建议的改进方案（后续版本）
1. 创建独立的 `brands`、`designers`、`categories` 表，每条记录有唯一 `id`
2. `tasks`/`styles` 表中存储外键 `brand_id`、`category_id` 等
3. 前端下拉框绑定 `id` 而非 `name`
4. 实现"级联更新"：改名时自动反映到所有引用位置

> **注意**：这是一个侵入性很大的底层架构重构，需要数据迁移脚本配合。建议在功能稳定后，作为 V6.0 的专项升级。

## 🔧 号型规格相关排障记录 (V5.3 Hotfix)

### 弹窗被遮挡问题
*   **根因**：`.glass` 容器的 `backdrop-filter: blur(20px)` 创建了独立的层叠上下文（CSS Stacking Context）。即使弹窗的 `.overlay` 设为 `position: fixed; z-index: 9999`，也无法突破父容器的层叠上下文。
*   **修复**：使用 `ReactDOM.createPortal` 将弹窗渲染到 `document.body`，物理上脱离 `.glass` 容器，从而不受其层叠上下文限制。

### 保存后白屏崩溃
*   **根因**：`categories` 从字符串数组升级为对象数组后，看板筛选区（行866）仍用 `{c}` 直接渲染对象，React 无法渲染对象导致组件树崩溃。
*   **修复**：所有消费 `categories` 的位置统一加入 `typeof c === 'string' ? c : c.name` 兼容处理。
