## 1. 产品定位

PatternMaster Pro 是女装打样管理桌面应用，服务于从设计稿到纸样、唛架、样衣、大货的全流程。
核心对象：**款式（style）**、**开发单（task）**、**版次（sample_type）**、**资料（drawings/bom/process）**。

## 2. 核心数据模型讨论：款 vs 单 vs 版次

### 2.1 现状模型

```
styles（款，style_no 唯一）
  └── tasks（开发单，一款可多张）
        └── drawings / bom_items / process_items / 工作动态（按 task_id 隔离）
款级共享：styles.pdf_url（设计稿）
```

- 一张开发单 = 一个打样版次（胚样/头版样/生产样）
- 建单时不查重款号 → 同一款可建多张单
- 版次（sample_type）是 task 的属性

### 2.2 暴露的问题

- AW26-JK001 存在 task1（胚样）和 task2（头版样）两张单，图纸只挂在 task2 下，task1 空
- SS26-TS003 同样存在 task4（胚样）和 task5（生产样）
- 看板同款多卡同名，用户困惑"我的设计稿在哪个单里"
- task1 的 status 曾为旧值 `in_progress`，不在看板三列枚举内 → 看板消失

## 3. 两种任务管理模式对比

### 3.1 模式 A：单=版次（现状/传统模式）

- **状态机维度**：为当前版次负责（progress_nodes 跟踪该版次打样进度）
- **资料归属**：按版次单隔离（task_id）
- **看板**：一版次一卡，同款多卡；可按版次筛选
- **款级进度**：需要更高维度仪表盘跨单聚合（当前缺失）

**优势**：版次进度精细独立；资料隔离不会误用；多版次并行互不阻塞；符合传统打样习惯。
**劣势**：看板同款多卡混乱；资料重复上传；款级整体进度不可见；建单不查重易重复。

### 3.2 模式 B：单=款（新工作流）

- **状态机维度**：为款式全流程负责（收单→胚样→头版样→...→大货）
- **资料归属**：款内共享，通过版本迭代管理（drawings.version V1/V2）
- **看板**：一款一卡，无重复
- **款级进度**：天然可见

**优势**：看板清爽；资料一次上传全版次可用；全流程一目了然；建单天然查重。
**劣势**：版次精细进度需在单内展开；多版次并行时总状态机表达力不足；资料共享可能导致版次间误用；存量需合并。

### 3.3 关键洞察（用户提出）

> 原来设计的状态机是只为当前版次负责的，而新设计的状态机是为当前款式全流程负责的——这是不同维度的任务管理模式。
> 原模式各版次资料隔离，新模式资料共享，只是通过版本迭代来管理。

两种模式各有优劣，不做非此即彼的选择，采用**混合模式**。

## 4. 推荐方案：混合模式（以款为主单 + 版次批次子状态）

```
款单（一张，看板一卡一款）
  ├── 款级状态机：全流程总进度
  ├── 版次批次列表（单内）：
  │     ├── 胚样批次：尺码/颜色/数量/优先级/日期/子状态
  │     ├── 头版样批次：...
  │     └── 生产样批次：...
  ├── 资料库（款内共享，带版本号）
  └── 版本绑定：每个批次可引用特定版本的资料
```

**同时获得**：一款一卡的清爽 + 款级全流程可见 + 版次精细子状态 + 资料共享防重复 + 版本绑定防误用 + 多版次并行支持。

## 5. 双视角分析（关键业务洞察）

系统使用者不同，关注粒度不同——这是混合模式的核心依据。

### 5.1 设计师视角（宏观，款级聚合）
- 总共开发了几个款式
- 每个品类的占比
- 当前款式开发进度：哪些在做胚样、哪些在做头样、哪些已确认可下大货

### 5.2 板师视角（微观，版次级明细）
- 手里的款哪些在打胚样、哪些在打头样
- 每个款的具体进度
- 样衣做了没有？没做的原因（欠面辅料？）
- 这件样衣是谁做的

### 5.3 设计结论：同一套数据，两种视图
- **数据层**：款式（顶层聚合）1──N 版次批次（板师工作单元）
- **视图层**：设计师仪表盘（款级聚合）⇄ 板师工作台（版次级明细），可切换
- **状态机分层**：
  - 款级状态（自动聚合，设计师看）：未开始/胚样中/头样中/复版中/可下大货/已完结——取最先进版次状态推导
  - 版次级状态（板师手动推进）：待配料/打版中/样衣中/待确认/已完成，带阻塞子状态（欠面辅料/待设计师确认/待工艺单）

## 6. 状态机设计演进

### 6.1 旧状态机：按分工角色

progress_nodes 按分工角色写死：配料 / 跟版 / 版师 / 样衣 / 工艺（状态机+联动）。

**问题**：实际工作流是按项目推进迭代的"项目更新流"，自由度更高，按角色写死无法适配。

### 6.2 新状态机：按项目推进

progress_nodes 改为用户可自由增删改的节点列表，每个节点有 label/status/date/by/note。
示例（26AWW526）：收单 → 胚样 → 完成头样待料 → 料齐下板房 → 完成头版样衣（乐祥芸）。

**原则**：status（看板追踪状态）与时间线解耦——status 由用户独立控制看板列，时间线只忠实记录过程，不反向驱动看板。

## 7. 资料管理策略

### 7.1 五分类

图纸资料分为：设计稿 / 参考图 / 成衣图 / 纸样 / 唛架图。

### 7.2 两类资料的不同策略（用户决策）

- **参考资料**（参考图/成衣图）：A 方案——防冗余（同文件 hash 去重，重复上传不入库）
- **工作成果**（设计稿/纸样/唛架图）：B 方案——可追溯（同文件名归组，版本递增 V1/V2，保留历史版本）

### 7.3 设计稿与图纸资料库的打通

设计稿上传后自动同步到图纸资料库（设计稿分类），可从资料库选稿更换。
更换流程：单击设计稿放大 → 底部「从资料库选」→ 点卡片选中 → 「确认更换」生效。

## 8. 决策记录（ADR）

### ADR-001：设计稿更换入口不依赖 hover

- **问题**：hover 浮出的图标按钮在豆包内置浏览器中不可靠，用户单击=放大、双击=打开文件，无法触发更换。
- **决策**：单击设计稿放大后，放大图底部提供「更换设计稿」「从资料库选」按钮；hover 组保留文字按钮作为桌面增强。
- **理由**：单击放大是用户确定能触发的交互，不依赖 hover 环境。

### ADR-002：从资料库选弹窗采用"点选+确认"两步

- **问题**：弹窗卡片内嵌 PdfThumb（单击放大/双击打开），点击卡片图片区域被预览交互拦截（stopPropagation），选择事件永不触发，更换不成功。
- **决策**：弹窗内 PdfThumb 禁用交互（interactive=false），点卡片=选中高亮，底部「确认更换」按钮生效。
- **理由**：用户明确要求"有确认的更换过程"；两步确认防止误操作。

### ADR-003：任务管理采用混合模式（款单+版次批次）

- **问题**：单=版次导致看板重复、资料隔离；单=款导致版次精细进度丢失、并行支持弱。
- **决策**：以款为主单，版次作为单内批次（带子状态），资料款内共享+版本绑定。
- **理由**：吸收两种模式优势，分阶段实施降低风险。
- **状态**：已全部实施（阶段 1-7 完成），双视角混合模式上线。

### ADR-004：看板状态枚举归一

- **问题**：旧数据 status=in_progress 不在看板三列（todo/doing/done）枚举内，task1 从看板消失。
- **决策**：数据归一（in_progress→doing）+ 代码兜底（未知状态归入待处理列）。
- **理由**：双保险防止脏值导致单据隐形。
