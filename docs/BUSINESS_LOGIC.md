## 1. 产品定位

PatternMaster Pro 是女装打样管理桌面应用，服务于从设计稿到纸样、唛架、样衣、大货的全流程。
核心对象：**款式（style）**、**开发单（task）**、**版次（sample_type）**、**资料（drawings/bom/process）**。

## 2. 核心数据模型讨论：款 vs 单 vs 版次

### 2.1 现状模型

```
styles（款，style_no 唯一）
  └── tasks（开发单，一款可多张）
        └── drawings / bom_items / process_items / 工作动态（按 task_id 隔离）
款级共享：styles.pdf_url（设计稿）
```

- 一张开发单 = 一个打样版次（胚样/头版样/生产样）
- 建单时不查重款号 → 同一款可建多张单
- 版次（sample_type）是 task 的属性

### 2.2 暴露的问题

- AW26-JK001 存在 task1（胚样）和 task2（头版样）两张单，图纸只挂在 task2 下，task1 空
- SS26-TS003 同样存在 task4（胚样）和 task5（生产样）
- 看板同款多卡同名，用户困惑"我的设计稿在哪个单里"
- task1 的 status 曾为旧值 `in_progress`，不在看板三列枚举内 → 看板消失

## 3. 两种任务管理模式对比

### 3.1 模式 A：单=版次（现状/传统模式）

- **状态机维度**：为当前版次负责（progress_nodes 跟踪该版次打样进度）
- **资料归属**：按版次单隔离（task_id）
- **看板**：一版次一卡，同款多卡；可按版次筛选
- **款级进度**：需要更高维度仪表盘跨单聚合（当前缺失）

**优势**：版次进度精细独立；资料隔离不会误用；多版次并行互不阻塞；符合传统打样习惯。
**劣势**：看板同款多卡混乱；资料重复上传；款级整体进度不可见；建单不查重易重复。

### 3.2 模式 B：单=款（新工作流）

- **状态机维度**：为款式全流程负责（收单→胚样→头版样→...→大货）
- **资料归属**：款内共享，通过版本迭代管理（drawings.version V1/V2）
- **看板**：一款一卡，无重复
- **款级进度**：天然可见

**优势**：看板清爽；资料一次上传全版次可用；全流程一目了然；建单天然查重。
**劣势**：版次精细进度需在单内展开；多版次并行时总状态机表达力不足；资料共享可能导致版次间误用；存量需合并。

### 3.3 关键洞察（用户提出）

> 原来设计的状态机是只为当前版次负责的，而新设计的状态机是为当前款式全流程负责的——这是不同维度的任务管理模式。
> 原模式各版次资料隔离，新模式资料共享，只是通过版本迭代来管理。

两种模式各有优劣，不做非此即彼的选择，采用**混合模式**。

## 4. 推荐方案：混合模式（以款为主单 + 版次批次子状态）

```
款单（一张，看板一卡一款）
  ├── 款级状态机：全流程总进度
  ├── 版次批次列表（单内）：
  │     ├── 胚样批次：尺码/颜色/数量/优先级/日期/子状态
  │     ├── 头版样批次：...
  │     └── 生产样批次：...
  ├── 资料库（款内共享，带版本号）
  └── 版本绑定：每个批次可引用特定版本的资料
```

**同时获得**：一款一卡的清爽 + 款级全流程可见 + 版次精细子状态 + 资料共享防重复 + 版本绑定防误用 + 多版次并行支持。

## 5. 双视角分析（关键业务洞察）

系统使用者不同，关注粒度不同——这是混合模式的核心依据。

### 5.1 设计师视角（宏观，款级聚合）
- 总共开发了几个款式
- 每个品类的占比
- 当前款式开发进度：哪些在做胚样、哪些在做头样、哪些已确认可下大货

### 5.2 板师视角（微观，版次级明细）
- 手里的款哪些在打胚样、哪些在打头样
- 每个款的具体进度
- 样衣做了没有？没做的原因（欠面辅料？）
- 这件样衣是谁做的

### 5.3 设计结论：同一套数据，两种视图
- **数据层**：款式（顶层聚合）1──N 版次批次（板师工作单元）
- **视图层**：设计师仪表盘（款级聚合）⇄ 板师工作台（版次级明细），可切换
- **状态机分层**：
  - 款级状态（自动聚合，设计师看）：未开始/胚样中/头样中/复版中/可下大货/已完结——取最先进版次状态推导
  - 版次级状态（板师手动推进）：待配料/打版中/样衣中/待确认/已完成，带阻塞子状态（欠面辅料/待设计师确认/待工艺单）

## 6. 状态机设计演进

### 6.1 旧状态机：按分工角色

progress_nodes 按分工角色写死：配料 / 跟版 / 版师 / 样衣 / 工艺（状态机+联动）。

**问题**：实际工作流是按项目推进迭代的"项目更新流"，自由度更高，按角色写死无法适配。

### 6.2 新状态机：按项目推进

progress_nodes 改为用户可自由增删改的节点列表，每个节点有 label/status/date/by/note。
示例（26AWW526）：收单 → 胚样 → 完成头样待料 → 料齐下板房 → 完成头版样衣（乐祥芸）。

**原则**：status（看板追踪状态）与时间线解耦——status 由用户独立控制看板列，时间线只忠实记录过程，不反向驱动看板。

## 7. 资料管理策略

### 7.1 五分类

图纸资料分为：设计稿 / 参考图 / 成衣图 / 纸样 / 唛架图。

### 7.2 两类资料的不同策略（用户决策）

- **参考资料**（参考图/成衣图）：A 方案——防冗余（同文件 hash 去重，重复上传不入库）
- **工作成果**（设计稿/纸样/唛架图）：B 方案——可追溯（同文件名归组，版本递增 V1/V2，保留历史版本）

### 7.3 设计稿与图纸资料库的打通

设计稿上传后自动同步到图纸资料库（设计稿分类），可从资料库选稿更换。
更换流程：单击设计稿放大 → 底部「从资料库选」→ 点卡片选中 → 「确认更换」生效。

## 8. 决策记录（ADR）

### ADR-001：设计稿更换入口不依赖 hover

- **问题**：hover 浮出的图标按钮在豆包内置浏览器中不可靠，用户单击=放大、双击=打开文件，无法触发更换。
- **决策**：单击设计稿放大后，放大图底部提供「更换设计稿」「从资料库选」按钮；hover 组保留文字按钮作为桌面增强。
- **理由**：单击放大是用户确定能触发的交互，不依赖 hover 环境。

### ADR-002：从资料库选弹窗采用"点选+确认"两步

- **问题**：弹窗卡片内嵌 PdfThumb（单击放大/双击打开），点击卡片图片区域被预览交互拦截（stopPropagation），选择事件永不触发，更换不成功。
- **决策**：弹窗内 PdfThumb 禁用交互（interactive=false），点卡片=选中高亮，底部「确认更换」按钮生效。
- **理由**：用户明确要求"有确认的更换过程"；两步确认防止误操作。

### ADR-003：任务管理采用混合模式（款单+版次批次）

- **问题**：单=版次导致看板重复、资料隔离；单=款导致版次精细进度丢失、并行支持弱。
- **决策**：以款为主单，版次作为单内批次（带子状态），资料款内共享+版本绑定。
- **理由**：吸收两种模式优势，分阶段实施降低风险。
- **状态**：已全部实施（阶段 1-7 完成），双视角混合模式上线。

### ADR-004：看板状态枚举归一

- **问题**：旧数据 status=in_progress 不在看板三列（todo/doing/done）枚举内，task1 从看板消失。
- **决策**：数据归一（in_progress→doing）+ 代码兜底（未知状态归入待处理列）。
- **理由**：双保险防止脏值导致单据隐形。

## 10. REQ 系列业务规则与决策（2026-09-07 ~ 09-08）

> 本节记录近期 REQ 迭代中沉淀的业务规则与用户拍板，属"AI 无法替代"的产品决策，持续维护。

### 10.1 信息归属：款级 vs 版次级（REQ-004，2026-09-07 拍板）

| 维度 | 款级（styles，共享载体） | 版次级（sample_runs，独立工作单元） |
|---|---|---|
| 字段 | 款号/名称/类别/品牌/设计师/年度/季节/波段、设计稿(pdf_url)、**版师(pattern_maker)** | 打样单号(order_no)、审核状态+审版意见、样衣工、尺码/颜色/数量/日期/优先级/子状态、尺寸表(size_data) |
| 原则 | 不依附任一打样单，款下共享 | 各版次独立记录、互不影响 |

- 打样单号 = `PO-{款号}-V{n}`（款内顺序 V0 起，删除不重排，max+1）
- 审核对象是具体样衣（审胚样/头版样/审生产样），意见跟随版次独立记录
- **版师已上移款级（REQ-015，2026-09-08 拍板，见 10.7）；样衣工维持版次级**

### 10.2 尺寸表体系（REQ-005，2026-09-07~08 六次验收定稿——用户最关心，规则写死）

**数据模型**：每个版次（sample_runs.size_data）拥有**独立尺寸表**，各版次数据隔离；旧 tasks.size_data 迁移至各款首个批次后清空（列保留兼容）。

**入口与锁定（用户三次验收后的最终形态）**：
- 基本信息页每张批次卡片有「尺寸表」按钮（Ruler 图标）→ 点击**锁定该版次**进入尺寸页
- 尺寸页顶部横幅「当前编辑版次（已锁定）：PO-XX-Vn（版次 · 尺码）」+ 注明"本页仅编辑该版次尺寸表、各版次数据隔离，编辑其它版次请返回基本信息页从其批次卡片进入"
- 尺寸页内**无任何切换版次控件**（曾做下拉/弹窗切换均被用户否决）
- 直接点「尺寸指标」Tab 进入 → 默认展示**最新编辑批次**（updated_at 最新），从批次卡片进入则绑定该卡片版次

**新批次尺寸表**：创建时从品类预设（measurement_templates）生成；无预设则空表（正确 fallback，不属缺陷）。

**跨版次对比（查看载体，无独立参考表）**：
- 对比下拉选择其它版次 → 主表「比对值」列紫色显示参考版次**同码**尺寸（码不同按放码规则换算）+ 差异增减量（如 +3.0/-12.0）
- 用户明确否决"弹窗/内嵌参考表"等任何独立参考表——比对值列即查看载体

**空表预览（复制场景）**：当前版次尺寸表为空 + 选中对比版次 → 表格自动以参考版次数据为**预览行**（浅拷贝、只读防误改、标准码留空占位"待导入"），虚线提示条说明来源；**先查看数据再决定导入**。

**导入（杜绝盲盒）**：查看确认合适后点「导入该版次数据到当前版次」→ 确认弹窗（来源版次+行数+覆盖警示）→ 整体覆盖导入。曾实现"从上一版次复制"（隐式来源）被否决；曾实现弹窗选批次导入也被否决——最终定型为**跨版次对比视图内先看后导**。

## 11. 技术经验（2026-09-08）

- **Vite 文件监听与测试目录**：vite dev 默认监听项目根目录（vite.config.js 无 server.watch.ignored 时）。
  E2E 测试若把浏览器用户数据目录（_chrome_*）放在项目根目录，Edge 运行中锁定 Sessions 文件，
  Vite FSWatcher 报 `EBUSY: resource busy or locked` → 未捕获 error → Vite 进程崩 → 整个 dev 服务挂。
  规范：① vite.config.js server.watch.ignored 忽略 `**/_*/**`、`**/_*.*`、附件/备份目录；② E2E userDataDir 一律放项目外（%TEMP%）。
  二度触发（2026-09-08 同日晚，非 E2E 目录）：编辑工具写文件生成的 `*.agent_infra_tmp*` 临时文件（如 docs/待开发文档.md.agent_infra_tmp_*）同样触发 EBUSY 崩溃。vite.config.js 追加忽略 `**/*.agent_infra_tmp*`，并在本环境实测（创建→删除临时文件，服务存活、无新 EBUSY）确认生效。
- **前端 E2E 断言规范**：断言"弹窗出现"必须校验可见性三要素——computed opacity === '1'、pointer-events === 'auto'、
  elementFromPoint(按钮中心) 命中按钮本体；仅断言 overlay DOM 存在会漏检透明/穿透层缺陷（REQ-016 教训）。
- **overlay 机制**：`.overlay` 默认 opacity:0 + pointer-events:none（REQ-006 侧边栏动画引入）；
  任何弹窗复用 `.overlay` 时必须同时加 `.overlay-show`，否则不可见不可点。
