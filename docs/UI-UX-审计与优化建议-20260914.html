Executive Summary

结论先行：底子很好，问题集中在"三处失守"

这个项目的设计意图和令牌体系明显高于同类内部工具的平均水平——三套主题、30+ 语义 token、 为旧内核浏览器显式双写变量、为编号数字单独启用等宽字体、给空单元格占位压暗降噪。 这些都说明设计者真正在意过"看起来怎么样"。问题不在于审美，而在于三处工程失守， 让已经做对的事情大量失效。

失守一 · 样式双轨制。src/index.css（1,230 行）与 src/styles/app.css（625 行） 并行存在且互相覆盖同一批选择器（≥96 处），同一元素同时被三层规则争夺（CSS 类 + 内联 + !important）。 这是"改一处、坏一处"的根源，也是历史上反复返工（如看板 hover 重叠修了三轮）的土壤。
失守二 · 令牌被绕过。全站 96 处内联 style 对象 + 119 处组件内硬编码色值， 直接绕开了 theme.css。后果已经发生：--app-bg（页面金色氛围光）被 App.jsx 一行内联样式彻底覆盖， 设计稿里的氛围渐变从未在实机上生效过；同时 5 个与"暖黑金"完全无关的蓝色/靛紫色散落在看板代码里。
失守三 · 可达性与响应式缺席。全站只有 1 条媒体查询，根容器却硬编码 min-width:1280px 且 overflow:hidden； Windows 常见的 125%/150% 显示缩放下视口不足 1280，右侧内容被裁切且没有任何滚动条可以补救。 键盘可达性方面：全项目仅 2 处 Escape 监听、4 条 :focus-visible、 所有弹窗无 role="dialog" / 无焦点陷阱 / 无法用 Esc 关闭。

按投入产出排序，最该先做的三件事

02 · Design System

设计令牌体检：体系完整，但颜色可达性有硬伤

src/styles/theme.css 定义了三套主题（自定义暖黑金 / 系统深 / 系统浅）， 共 30+ 语义 token，且全部显式双写而非依赖 light-dark() / color-mix()—— 这是为了兼容豆包内置浏览器等旧内核，并在文件头留了原因注释。这种"为边缘环境做设计"的意识很专业。 问题出在中性灰阶的取值。

03 · Findings

问题清单：17 项，按修复优先级分级

P0 · 阻断级（3 项）

P0-11280px 硬约束 + overflow:hidden：缩放屏用户被裁切且无法补救

证据

src/App.jsx:269-277 根容器同时设置了 minWidth: 1280 与 overflow: 'hidden'：

<div className="app" style={{ height:'100vh', overflow:'hidden',
     minWidth: 1280 // 设置最小宽度，防止窄屏下控件强行压缩变形导致堆叠
}}>

注释里的意图是合理的（防止控件堆叠变形），但手段选错了——用"禁止收缩"解决了"收缩变形"，代价是"不可用"。

影响

Windows 常见的显示缩放会让逻辑视口宽度远低于物理宽度：

物理分辨率缩放比实际 CSS 视口结果
1366 × 768125%≈ 1,093 px裁切 ≈187px，无滚动条
1920 × 1080150%≈ 1,280 px正好卡在临界，窗口边框一挤就裁
2560 × 1440175%≈ 1,463 px安全

被裁掉的正是顶栏右侧的「导出工艺单 / 导出 PDF / 历史版本 / 删除单据」和看板最右一列。 因为 overflow:hidden，用户连横向滚动条都没有——没有任何自救手段，只能改系统缩放或换大屏。

建议
  1. 删除 minWidth（或降为 960 仅作极端兜底）；根容器 overflow 改 'auto'。
  2. 用容器自适应 + 断点收缩替代硬约束：顶栏操作按钮在窄视口折叠成一个「⋯」溢出菜单。
  3. 看板列宽改流体：clamp(340px, 30vw, 520px)，替代固定的 500px（见 P1-6）。

P0-2文字对比度不达标：--text-3 3.3:1、--text-4 2.0:1，placeholder 实测 1.35:1

证据

src/styles/theme.css:21-22：

--text-3: #6b6560;   /* 3.3:1 — 低于 AA 4.5:1 */
--text-4: #4a4540;   /* 2.0:1 — 严重不足 */

src/styles/app.css:660 又给 placeholder 叠了第二层衰减：

.data-table input::placeholder { color: var(--text-4); opacity: .5; }

合成后的实际灰度约 #2c2a28，对比度 1.35:1——已低于"可察觉"阈值，接近纯装饰。

影响

被击中的是信息密度最高的一层：尺寸表 / BOM / 工艺指示的表头、所有表单标签、 看板卡片的 .bento-node-date（10px 的进度节点日期）、侧栏版本号（11px）、 所有输入框占位、空态提示。用户要么眯眼，要么误判为"这里没数据"。

更麻烦的是方向性错误：小字号（10–12px）对对比度的要求本应更高， 而当前设计是"字号越小、颜色越淡"。

建议
/* theme.css — custom 主题 */
--text-3: #6b6560;   --text-4: #4a4540;
--text-3: #8c857c;   /* ≈4.8:1 — 表头/标签达标 AA */
--text-4: #6b6560;   /* ≈3.3:1 — 仅限装饰/分隔线语义，不再用于正文 */

/* app.css — 去掉二次衰减，占位改由 --text-3 承担 */
.data-table input::placeholder { color: var(--text-4); opacity: .5; }
.data-table input::placeholder { color: var(--text-3); opacity: .75; }

配套：把 --text-4 的用途收敛为"分隔/装饰"，代码层做一次全量替换审计 （grep -rn 'text-4' src/ 目前命中数十处，其中约 1/3 属于误用）。

P0-3弹窗体系无 Esc 关闭、无焦点陷阱、无 ARIA 语义

证据

全项目搜索 Escape 只有 2 处命中，且都不是"关闭弹窗"，而是取消行内编辑：

  • PeopleEditor.jsx:109 / :135 — 取消姓名/角色编辑态
  • SettingListEditor.jsx:40 — 取消行内编辑

而所有弹窗都是裸 div + 点击遮罩关闭的结构，例如 NewTaskModal.jsx:76：

<div className="overlay overlay-show" onClick={onClose}>
  <form className="modal glass" onSubmit={submit}>

涉及组件：ConfirmModal · NewTaskModal · ExportButton 确认框 · PdfPickerModal · VersionHistoryModal · OperationLogsModal · MeasurementModal · PdfThumb 大图预览 · DrawingLibrary 上传/版本弹窗。 全部无 role="dialog"、无 aria-modal、无 aria-label、 无焦点陷阱、无背景 aria-hidden。

影响
  • 键盘用户无法关闭弹窗，只能 Tab 摸索到右上角 ×（若焦点被背景元素截获则永远出不去）。
  • 打开弹窗后 Tab 会跑到背后页面的按钮上——视觉上"在弹窗里"，实际在操作背后的看板。
  • 屏幕阅读器不会播报"对话框已打开"，读完弹窗内容会继续读背景。
  • PdfThumb 的大图预览层是整屏可点关闭，极易误触关闭（想放大看细节，点了一下图片就没了）。
建议

抽出 <Modal> 基座组件，把现在 9 处各写一遍的弹窗骨架收敛到一处：

// src/components/common/Modal.jsx — 统一承载以下职责
Esc 关闭            document.addEventListener('keydown', …'Escape')
焦点陷阱            Tab 循环限制在弹窗内（首/末元素回绕）
焦点归还            关闭后 focus() 回触发元素
背景隔离            root 加 aria-hidden + 禁止背后滚动
语义               role="dialog" aria-modal="true" aria-labelledby={titleId}
遮罩容错            仅当 mousedown 与 click 都落在遮罩上才关闭（防拖选文本误关）

优先级说明：如果短期内不做完整基座，至少先补两件事—— (1) 全局 Esc 关闭最上层弹窗；(2) PdfThumb 放大层把"点图片即关"改为"仅点空白/× 关闭"。

P1 · 体系级（7 项）

P1-1样式双轨制：index.css 与 app.css 互抢 ≥96 处选择器

证据

src/main.jsx:3-5 按顺序引入三个样式表：

import './index.css'        // 1,230 行
import './styles/theme.css'  //   129 行 — 令牌
import './styles/app.css'    //   625 行

其中 index.css 有 96 行命中了与 app.css 同名的选择器 （.data-table · .modal-overlay · .modal-content · .modal-sidebar · .modal-main · .template-grid · .template-card · .side-nav-item · .cat-item · .del-btn · .sidebar-v4 · .settings-content · .table-wrapper · .size-table-container · .sort-actions · .btn-sort · .table-checkbox · .tcard-name · .tpl-table …），且取值不同。

最典型的冲突——同一个 .col（看板列）被三层规则同时争夺：

/* index.css:1148 (后加载，!important 胜出) */
.col { min-width:600px !important; max-width:600px !important; flex:0 0 600px !important; }

/* styles/app.css:117 */
.col { width:400px; flex:0 0 400px; }

/* KanbanView.jsx:480 — 内联，优先级最高 */
<div className="col" style={{ width:500, flex:'0 0 500px' }}>

另有 .btn-danger 在 app.css 内部被定义两次 （:548 红底圆角大按钮 / :631 深红底小按钮，padding 与圆角都不同）。

此外 src/App.css（37 行）是 Vite 脚手架残留（#root{max-width:1280px} · .logo{height:6em} · logo-spin）， 未被任何文件 import 的死文件；一旦有人顺手引入，会直接摧毁顶栏 logo。

影响

这是全部视觉问题的系统性根因。表现是：改一处样式不生效 → 加 !important → 别处坏 → 再加内联兜底 → 下一轮更不敢动。ITERATION_STATE.md 里"看板卡片 hover 与 sticky 列头重叠"修了三轮才定位到 .col-body 缺 padding-top，正是这种环境下"症状当病因治"的典型。

建议
  1. 建立单一 CSS 入口 + 分层目录：tokens.css（令牌）→ base.css（reset/全局）→ components/（按组件拆）→ views/（按视图拆）。
  2. 删除 src/App.css；把 index.css 中仍有效的规则迁移后清空。
  3. 全部 !important 清零（当前散布在 .col · .data-table 系列 · .bento-* 等数十处）， 改用更具体的选择器或 CSS 变量替代。
  4. 把 .col 宽度从内联收回 CSS：.col{--col-w: clamp(340px,30vw,520px); width:var(--col-w); flex:0 0 var(--col-w);}

P1-2令牌被绕过：96 处内联 style + 119 处硬编码色值，--app-bg 从未生效

证据

内联样式分布（style={{...}} 计数，共 96 处 / 25 个文件）：

SizeTable.jsx 46   KanbanView.jsx 45   DrawingLibrary.jsx 34   DetailView.jsx 27
BomEditor.jsx 26   ProcessEditor.jsx 23   DesignerDashboard.jsx 20   PdfPickerModal.jsx 20
SampleRunList.jsx 15  OperationLogsModal.jsx 14  ExportButton.jsx 13  …

硬编码色值（hex / rgba 计数，共 119 处）：DrawingLibrary 23 · KanbanView 18 · SizeTable 13 · PdfThumb 7 · DesignerDashboard 7 …

已发生的实际后果：氛围光被覆盖

/* theme.css:39 — 设计稿里的金色氛围渐变 */
--app-bg: radial-gradient(circle at top right, rgba(200,169,110,.05), transparent 40%), …;

/* app.css:7 */
.app { background: var(--app-bg); }

/* App.jsx:273 — 内联优先级最高，上面两条全部失效 */
<div className="app" style={{ …  background: 'var(--bg)'  … }}>

结论：--app-bg 在三套主题里都定义了，但从未在界面上渲染过。 实机界面比设计稿更"平"，缺少那层暖光。

另一类后果：主题切换时局部破色。多处用 color: var(--text) 涂在彩色底上：

/* app.css:548 / :127 — 红底 + --text 文字 */
.btn-danger        { background:#ef4444; color: var(--text); }
.bento-overdue-badge { background:rgba(239,68,68,.92); color: var(--text); }

自定义 / 深色主题下 --text 是浅色，尚可；但切到系统浅色主题时 --text 变成近黑（CanvasText），于是红底黑字——危险按钮的可读性直接崩掉。

第三类：色板越界。暖黑金体系明确写着"深浅主题零蓝色"，但看板代码里散落着 #6366f1（靛蓝，KanbanView:150）、#f43f5e / #fb923c / #f59e0b / #eab308 等与体系无关的状态色。

建议
  1. 删掉 App.jsx:273 的内联 background（一行改动，立刻找回设计稿氛围光）。
  2. 把状态语义色提升为令牌，三套主题各给一套： 
    --state-run-waiting / pattern / sample / pending / done
--state-prio-s / a / b / c      --state-audit-pass / wait / reject
--state-overdue / today / soon  --state-danger / danger-text

P1-6SmartSelect 打开期间以 rAF 逐帧读取布局：每帧强制重排

证据

src/components/common/SmartSelect.jsx:39-54：

useEffect(() => {
  if (!open) return;
  const el = ref.current; if (!el) return;
  let raf;
  const tick = () => {
    const r = el.getBoundingClientRect();   // ← 每帧强制同步布局
    setPos(prev => …);
    raf = requestAnimationFrame(tick);          // ← 无限循环，直到关闭
  };
  tick();
  return () => cancelAnimationFrame(raf);
}, [open]);

注释说明动机是"弹窗/容器布局变化时弹层实时同步，不再跑偏"——需求真实（新建弹窗异步查重会插入提示区块导致弹窗上移）。 但用每帧轮询解决一个离散事件问题，代价过大。 注意 setPos 里做了 prev 相等判断避免重渲染，所以问题不在 React，而在 getBoundingClientRect() 本身每帧强制触发一次同步 layout。

影响

下拉展开期间主线程持续被 layout 占用。在尺寸表（数十个受控 input）或图纸库（数十张缩略图）这类重页面上， 会与动画/输入竞争主线程 → 掉帧、输入延迟；笔记本上则是持续耗电。 用户感受可能是"下拉打开后输入有点跟手不上"。

建议

把"持续轮询"换成"事件驱动 + 兜底低频"：

// 只在真正会改变锚点位置的事件上重算
window.addEventListener('scroll', reposition, { capture:true, passive:true });
window.addEventListener('resize', reposition, { passive:true });
const ro = new ResizeObserver(reposition); ro.observe(document.body);
observer.observe(dialogEl, { attributes:true, attributeFilter:['style','class'] });

// 兜底：仅在打开后的前 600ms 内低频轮询（覆盖异步插入提示区块的场景）
const t = setInterval(reposition, 100); setTimeout(() => clearInterval(t), 600);

若愿意引依赖，@floating-ui/dom 的 autoUpdate() 正是为这个场景设计的 （内部用 ResizeObserver + IntersectionObserver + scroll 监听，且带节流）。

04 · Root Cause

根因链：一个"双轨 CSS"如何生产出 17 个症状

上面 17 项问题里，至少 7 项可以由同一条因果链解释。理解这条链，比逐条修症状更重要。

历史演进单文件 App.jsx 内嵌 CSS 字符串 → 拆分组件时把 STYLES 抽成 app.css，但更早的 index.css 原样保留
→
双轨并行两份样式表同时加载，≥96 处选择器重名、取值不同
→
优先级失效改类名不生效 → 加 !important → 又被内联盖过 → 再加内联
→
三层争夺同一元素被 CSS 类 / !important / 内联同时定义（.col 是标本）
症状 A改动成本高 → 次要问题被搁置（对比度、响应式、焦点环）
→
症状 B新需求用内联快改 → 令牌被绕过 → --app-bg 失效、主题切换破色
→
症状 C同类问题反复出现 → 历史上"三轮才修对 hover 重叠"
关键判断：先做 P1-1（合并双轨 CSS）的性价比远高于它的工作量。 它本身不产生任何新功能，但它会把后面每一次 UI 迭代的成本砍掉一大截—— 包括你现在正在推进的每一轮视觉重构。

建议顺序：P0-1 / P0-2（各 1 小时以内，立竿见影）→ P1-1（合并样式，1–2 天）→ P1-2 + P2-4（令牌收敛）→ 其余按批次推进。
