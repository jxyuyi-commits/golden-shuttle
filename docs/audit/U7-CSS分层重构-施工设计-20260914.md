## 1. 分层方案

### 1.1 目标文件结构（`src/styles/` 单一入口 + 四层）

```
src/styles/
  tokens.css      ← 由现 theme.css 改名/保留：:root + [data-theme=custom|dark|light] + @supports 旧内核兜底
  base.css        ← 复位与全局基线：*,::before,::after / html,body / 字体 / ::selection / 滚动条 / @keyframes / .app 外壳 / .glass* / .mono
  components.css  ← 可复用组件：按钮族(.btn-*/.icon-btn/.op-btn)、表单族(input/select/.field/.dp-*/.ss-*/.smart-select)、表格族(.data-table/.mini-table/.tpl-table*/.table-wrapper/.sticky*/.sort-actions/.btn-sort/.grid-cell/.row-ops)、弹窗族(.modal*/.overlay/.sidebar/.confirm-modal/.version-*)、卡片族(.card/.bento-*/.glass-card/.drawing-*/.template-*/.setting-*/.people-*/.run-*/.dash-*/徽章 .tcard-*/.tag-*)
  views.css       ← 视图骨架与仅单视图使用的类：.board/.col/.col-*/.tab-bar/.tab/.detail-content/.settings-container/.top-settings-grid/.main-settings-area/.dashboard-view/.drawing-grid/.top-bar/.header/.logo
```

**`index.css`、`app.css`、`App.css` 三个文件全部删除**（`App.css` 本就是死文件；`index.css`/`app.css` 内容按规则分流后删除）。

### 1.2 判定规则（哪条规则搬到哪个文件）

1. 定义 CSS 自定义属性 / `color-scheme` / 主题选择器（`:root`、`[data-theme=*]`、`@supports` 兜底）→ **tokens**
2. 命中 `html/body/:root`、通配 `*`、纯元素选择器、伪元素/滚动条、`@font-face`、`@keyframes`、字体与抗锯齿、应用外壳 `.app` → **base**
3. 类可被 **≥2 个视图**复用的"组件类"（按钮/表单/表格/弹窗/卡片/徽章/下拉）→ **components**
4. 类只服务**某个具体视图的布局容器**（看板骨架 `.board/.col`、详情 `.tab-bar/.detail-content`、设置 `.settings-container/.main-settings-area`、仪表盘骨架、顶栏 `.top-bar/.logo`）→ **views**
5. 一条选择器在旧两轨/两代里出现多次 → 只保留 §2「建议保留」的取值，其余全删；若两条**属性互补无真冲突** → 合并成**一条**

### 1.3 `main.jsx` 新导入顺序与原因

```jsx
import './styles/tokens.css';      // 1 变量最先（供后续所有层消费）
import './styles/base.css';        // 2 复位与基线
import './styles/components.css';  // 3 组件
import './styles/views.css';       // 4 视图（最后，可对同特异性组件规则做局部覆盖而无需 !important）
```

**为什么顺序是本次成败关键**：层叠对**同特异性**声明按**源序**裁决。历史 `!important` 的绝大多数（§3-b）源于"组件/视图规则写在被后加载的 app.css 通用规则之前"，只能靠 `!important` 反压。把 `components → views` 放到 `base` 之后、更具体规则写在更后，同特异性即自然胜出 → `!important` 可全删。

**不要用 `@layer`**：`theme.css:7-9` 明确记录"旧内核浏览器（豆包内置浏览器）不支持现代函数"的教训；`@layer` 同属现代特性，为一致性风险。改用**纯源序分层**。

## 4. `.col` 单一来源方案

**当前实渲值链**（元素 `<div className="col" style={{width:500,flex:'0 0 500px',boxSizing:'border-box'}}>` 在 `.board`(flex) 内）：
- `width` → 内联 500（`app.css:117` 的 400 被内联压死，**死声明**）
- `min/max-width` → `index.css:1148` 的 600（`!important` 压过内联与 `index.css:43` 的 720）
- `flex` → `index.css:1148` 的 `0 0 600px`（`!important` **压过内联**）→ flex-basis 600 决定宽度
- `display/flex-direction` → `app.css:117` 的 flex/column
- ⇒ **实渲宽度 600px**；`index.css:43`(720)、`app.css:117`(400)、内联(500) **全是死值** —— 这就是"改 `.col` 要试三次"的完整机理。

**方案：**

```css
/* tokens.css */
:root, [data-theme="custom"] { --board-col-w: 600px; }
```
```css
/* views.css —— 全站唯一 .col 定义 */
.board { display: flex; gap: 48px; overflow-x: auto; padding: 0 32px 32px; }
.col {
  flex: 0 0 var(--board-col-w);
  width: var(--board-col-w);
  min-width: var(--board-col-w);
  max-width: var(--board-col-w);
  display: flex; flex-direction: column; box-sizing: border-box;
}
```

- **删除**：`index.css:43`、`index.css:1148`、`app.css:117`。
- **`KanbanView.jsx:480`**：整段删掉 `style={{ width:500, flex:'0 0 500px', boxSizing:'border-box' }}`（值全部由 `.col` 变量提供）。改宽度时只动 `--board-col-w` 一处。
- **`app.css:117` 去留**：**删**（不在媒体查询内，是无条件死规则）。将来做响应式（U22）时**改 token** 而非加规则：
  `@media (max-width: 1440px) { :root { --board-col-w: 480px; } }`

**结论与建议顺序：U1 → U2 → U7**（与 roadmap 依赖一致）。**U1、U2 必须先落地并各自回归**，再由 U7 在 S2 一次性把 `app.css`/`theme.css` 内容并入新分层 —— 否则 U7 重写后会**覆盖掉 U1/U2 的改动**。

**具体交互点：**
1. **U1 ↔ U7 `.col`**：U1 把根容器改为可横向滚动后，窄屏只能靠**内层 `.board` 自己滚**。因此 U7 的 `.board{overflow-x:auto}` 与 `.col{flex:0 0 var(--board-col-w)}` **必须保留横向滚动**（不能改成 `flex-wrap`/`min-width:0` 收缩），否则 U1 的"无裁切"失效。二者**耦合但文件不重叠**。
2. **U1 的 `.app` 外壳**：U7 迁入 base.css 时**照搬 U1 后的版本**，不回落。
3. **U2 ↔ U7 tokens 层**：**推荐保留 `theme.css` 文件名**，把「tokens 层」就视为 `theme.css`，减少一次改名与 U8/U11 之后的连锁。若坚持改名，必须在 U2 之后执行。
4. **`--app-bg` 氛围光**属 **U3**；U7 迁 `.app{background:var(--app-bg)}` 时**不要顺手删 App.jsx 内联**。
5. **U22 响应式**（依赖 U1,U7）应写在 **views.css**（或改 `--board-col-w` token），不要回填 app.css。
