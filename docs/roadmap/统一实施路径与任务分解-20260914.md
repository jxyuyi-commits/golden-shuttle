### A2. 正面回答：工程 P0 与 UI/UX P0 谁先做

**结论：工程 P0 先，但批 1 内两轨并行，UI 止血不必等工程 P0 全部完成。**
理由（针对"单机自用 + UI 刚重构 + 真实生产数据"）：
1. **不可逆性排序**：工程 P0-1「回滚清空尺寸表」是**确定性、可复现、无需异常操作**的数据丢失（每次回滚必触发），且直接作用于用户真实生产数据；UI P0-1 缩放裁切是"部分场景不可用"、可改系统缩放自救；P0-2 对比度是"可读但费眼"。**不可逆 > 可逆**。
2. **成本非对称**：工程 P0-1/P0-2 修复各为"改一两行"，半天内可全部落地；不存在"先做 UI 更划算"。
3. **UI 不必让路**：U1（删 `minWidth`+`overflow:auto`）、U2（四个文字令牌）触的是 `App.jsx`/`theme.css`/`app.css`，与工程侧 `server/**` **文件零重叠**，可同批并行、零冲突。
4. **迁移护栏优先级最高**：P0-3（迁移无备份）是"一次失败升级＝生产数据不可逆丢失"，且是 v21 的前置依赖，列为批 1 第一件事。

### A3. 并行 / 串行约束（依赖理由）

- **必须串行**：`迁移备份护栏(G4) → v21 清僵尸列(G10) → priority 单主(G11)`。理由：清列前必须先有"升级失败可回滚的备份点"；priority 权威归属取决于僵尸列清理后的数据模型。

## C. 备份迁移方案（决策 5）

**安全移动步骤**
1. **先校验完整性（读码/只读命令）**：清点三树文件数与总大小；对 `golden-shuttle-git-backup` 跑 `git fsck`，并用 `git log --branches --not --remotes` 确认**是否存在未推送 commit**；确认 122MB zip 未被进程占用。
2. **目标目录命名**：新建 `D:\开发历史文件备份\`，内部建 `golden-shuttle_backup_v5_2_stable\`、`golden-shuttle-git-backup\`、`golden-shuttle-migration-20260904.zip`，并建 `_README.md` 记录来源/日期/用途/文件数。
3. **移动命令要点**：优先 `robocopy "<src>" "<dst>" /MOVE /E /R:1 /W:1`（原生、可续跑、保留属性）；**不要**跨盘资源管理器拖拽（2.5 万文件易中断）。移动 = 复制+删源，全程不放回。
4. **移动后校验**：源目录已空；目标文件数/大小与移动前一致；`git -C D:\dev\golden-shuttle status` 干净；应用能正常启动并读写库。
5. **项目内索引**：建议在 `docs/archive/` 留一行说明（"备份树已迁至 `D:\开发历史文件备份`，含日期与用途"），不进 git 大文件。

**风险点**
- 2.5 万文件跨盘移动为分钟级、中途断电可能半移 → `robocopy /MOVE` 可重跑续传。
- `golden-shuttle-git-backup` 若含未推送 commit：**先** `git bundle create` 备份或推送远端，**再**移动，避免丢历史。
- 移动期间确保 `golden-shuttle` 本体未启动（避免 db/uploads 被锁）。
- 【推测】zip 单文件移动本身极快，风险仅在于是否被占用。

## D. 前后端拆分前瞻约束（决策 7 · 新增重点）

> 方向：**现在只做单机**；成熟后再拆。原则：**只留低成本、对象稳定的"缝"，不为未来做过度抽象。**

**① 后端安全模型**：现状（**读码确认**）`index.cjs` 回环绑定 `localhost`、CORS 白名单且 `!origin` 放行、**零鉴权中间件**。留缝：把 CORS 白名单/端口/路径抽成 `config.cjs` 集中常量，并在管线中预留一个 no-op 的"鉴权前置中间件"位置——未来接用户认证只改一处。

**② Electron 专有能力**：留缝 vs 不动，逐项取舍。
- `files.openLocally`：**读码确认**当前**并非**用 Electron `shell`，而是 `exec('start "" ...')` 调 Windows cmd（本身就是 P0-2 根源）。→ **做**：抽独立"本机能力"模块（`capabilities/localOpen.cjs`），本机走 `shell.openPath`，服务器端返回"不支持/降级下载"。低成本且与 G2 复用。
  > **执行注记（2026-09-15，G17 已落地 `ffc5adf`）**：本行"读码确认"**已过期**——G2 之后 `openLocally` 实际已是 `shell.openPath` + **无 Electron 时 `rundll32 url.dll,FileProtocolHandler`（execFile + argv，不经 shell）** 回退，而非 `exec('start "" ...')`。故 G17 落地采用**三级能力**（`electron-shell` → `windows-fallback` → `unsupported`），而非本行字面的"无 shell 即降级"——后者会改变**开发态单跑后端（无 Electron）**的行为、违反行为等价红线。`unsupported` 分支保留，供将来服务器端降级为下载。教训：**计划文档的读码结论会随改造过期，落地前必须重核现状。**
- `thumbs.cjs`：EMF→PNG 依赖 `spawn powershell.exe` + Windows System.Drawing（**平台专属**）；DXF→SVG 为纯 Node（可移植）。→ **做**：把 EMF 转换封装为可替换能力（接口化，不预写跨平台实现）；DXF 解析原样复用。**不做**跨平台实现。
- 生产库路径 `%APPDATA%`（`main.js:95`）：路径已通过 `initDatabase(dbPath)` 参数注入、**未硬编码进 services**——**隔离度已足够，无需改动**。

**③ 数据层**：**读码确认** SQL 与 better-sqlite3 专有 API 扩散程度**高但集中**：`db.prepare/exec` 出现在 `db.cjs` + 11 个 service（tasks 24、versions 20、sampleRuns 20、drawings 10…）；`db.transaction`/`PRAGMA`/`ALTER TABLE DROP COLUMN` 主要在 `db.cjs` 与少数 service。结论：`services/` **隔离了 HTTP 层但未隔离 SQL 方言**（SQL 字符串直写在 service 内）。**做**（低成本）：把迁移执行器改为 `runMigrations(db)` 参数化（把模块级单例依赖显式化）；**不做**：现在不引入 repository/ORM、不抽 DB 驱动抽象接口、不做多租户/多库——业务仍在高速演进，过早抽象对象不稳定。

**④ 前端硬编码**：`client.js:7` `window.location.origin.includes('5173')` 决定 API base。**做**：改为读取 `import.meta.env.VITE_API_BASE`（回退现有逻辑），零行为变化，一行成本。

**⑤ 迁移体系**：**读码确认** `migrations = [{version, up}]` + `_migrations` 表，但 `up()` 闭包**直接引用模块级 `db` 单例**（`db.cjs:6`）——这是未来多库/多租户复用的**最大障碍**。留缝即 D③ 的 `runMigrations(db)` 参数化；**不做**多库运行时。

**现在做 vs 不做 一览**：做 = ① config 外置 + 鉴权占位、② `openLocally` 能力接口化、③ `runMigrations(db)` 参数化、④ `VITE_API_BASE` 外置（共 4 项，均低成本、对象稳定）。不做 = ORM/repository 层、DB 驱动抽象、EMF 跨平台实现、多租户/多库、用户表/权限模型。
