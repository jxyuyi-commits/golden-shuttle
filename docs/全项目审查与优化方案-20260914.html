P0-1回滚历史版本会静默清空尺寸表已复核
尺寸表已按 REQ-005 下沉到批次（sample_runs.size_data），但版本快照与回滚逻辑没跟上。
根因
versions.cjs:49 给每个 batch 无条件写入 size_data: parse(r.size_data, [])，键恒存在；因此 versions.cjs:159 的判定 hasRunSd = snapRuns.some(r => r.size_data !== undefined) 恒为 true。
后果
① 本应兜底的"兼容旧快照"分支 versions.cjs:165-169 成为不可达死代码；② 回滚任何历史版本都会把批次尺寸表写成 []；③ 旧快照里真实存在的 snap.size_data（versions.cjs:38，取自 tasks 级）永远不会被恢复。
触发
详情页 → 历史版本 → 回滚。无需任何异常操作。
修复
删除 :49 的无条件注入，改为仅在 r.size_data !== undefined 时写入键；或把 :159 的判定改为 snapRuns.some(r => Array.isArray(r.size_data) && r.size_data.length)。同时 :38 改从首个批次读取。

2.2 关键判断：IPC 双通道该留还是该砍

建议：收敛为纯 HTTP，删除双通道适配层。

理由：① 现实是 Express 无论如何都必须常驻（承接 18 个端点 + 大文件上传 + 生产 dist 托管）；② 因此 IPC 一条收益都没兑现——端口占用、ABI、影子锁全部原样存在；③ 反而新增三处必须同步的白名单与两套错误语义；④ 真正走向纯 IPC 需要重写 base64 大文件上传并放弃 localhost 调试便利，代价明显大于收益。

落地方式：client.js 回归纯 fetch，业务层 api/index.js 零改动（46 个接口签名不变）；preload.js/main.js 的 IPC 注册可保留待未来一次性纯 IPC 重构时复用。若未来确要"消除端口"，应作为独立一次性重构，而不是长期维持半成品。

6.2 测试怎么起步（现实约束下的最小方案）
